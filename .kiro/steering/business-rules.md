# Business Rules — Financial Calculations & Data Integrity

This file defines the CANONICAL formulas and data sources for all financial calculations in the system. These rules are IMMUTABLE. Any code that computes sales, revenue, quota, shift totals, or membership renewals MUST follow these rules exactly. Do NOT create alternative computation paths, do NOT duplicate these formulas in new locations, and do NOT change the data source for any calculation without updating this file first.

## 1. Sales & Revenue

### 1.1 Transaction Total (Single Sale)

- Formula: `sum of (item.quantity * item.price)` for all items in the cart
- Computed ONCE in `CheckoutService.checkout()` as `cartItems.reduce((sum, item) => sum + item.subtotal, 0)`
- Stored in `transactions/{id}.totalAmount`
- This is the ONLY place a transaction total is calculated. No other service or component may compute it differently.

### 1.2 Daily Sales Total

- Source of truth: `daily_sales/{YYYY-MM-DD}.totalSales`
- Written atomically during checkout: `increment(total)` on the daily_sales doc
- Decremented atomically during void: `increment(-totalAmount)` on the daily_sales doc
- Date key format: `YYYY-MM-DD` in LOCAL timezone, generated by `toLocalDateStr(date)` from `date.utils.ts`
- If data is suspected to be out of sync, use `DailySalesService.recalculateSalesForDay(date)` which rebuilds from `transactions` collection, excluding `status === 'VOID'`
- NEVER compute daily sales by client-side aggregation of transactions in components. Always read from `daily_sales` collection.

### 1.3 Monthly Sales Total

- Source of truth: `daily_sales` collection, summing `totalSales` for all docs where doc ID falls within the month range
- Computed in `DailySalesService.getMonthlySalesReport(year, month)` which queries `daily_sales` by document ID range (`YYYY-MM-DD`)
- Cached via `ReportStateService.getMonthlyReport(year, month)` with `shareReplay({ bufferSize: 1, refCount: true })`
- The `total` field in the returned `{ days: DailySales[], total: number }` is the monthly total
- This is the ONLY way to get monthly sales. All consumers MUST use `ReportStateService.getMonthlyReport()` or `DailySalesService.getMonthlySalesReport()`.
- NEVER compute monthly sales by summing transactions client-side. The `daily_sales` collection is the pre-aggregated source.
- If monthly data is suspected to be out of sync, use `DailySalesService.recalculateSalesForMonth(year, month)` which rebuilds daily_sales docs from `transactions` collection.

### 1.4 Sales by Staff (User)

- Computed in `ReportStateService.getUserSalesReport(userId, date)` which:
  1. Queries `transactions` filtered by `staffId === userId` and date range
  2. Uses `TransactionService.getSalesTotal()` with `getAggregateFromServer(sum('totalAmount'))` for the total
- The server-side aggregation (`getAggregateFromServer`) is the authoritative total. Client-side `reduce()` on the transaction list is for display breakdown only.
- VOID transactions are NOT explicitly excluded in the staff query (they should be — this is a known gap). If fixing, add `where('status', '==', 'COMPLETED')` to both the transaction query and the aggregate query.

### 1.5 Sales Analytics (Reports Dashboard)

- Computed in `ReportsService.getSalesAnalytics(startDate, endDate)` which queries `transactions` collection
- Aggregates: daily sales, top spenders, top products, staff performance
- VOID transactions are excluded via `if (tx.status === 'VOID') return` in the iteration
- This is a REPORT-ONLY computation for the admin dashboard. It reads from `transactions` (not `daily_sales`) because it needs line-item detail (products, staff, members).
- The daily sales totals from this report may differ slightly from `daily_sales` collection if there are unreconciled voids. The `daily_sales` collection is the authoritative source for totals; this report is for breakdown analysis.

### 1.6 Sales Analytics (Store Stats Page)

- Computed in `TransactionService.getSalesAnalytics()` which queries `transactions` (limit: 1000)
- Calculates: `totalRevenue`, `monthlyRevenue`, `todayRevenue`, `topSelling`, `lowPerformance`
- VOID transactions excluded via `if (tx.status === 'VOID') return`
- Date ranges use local `new Date()` for month/day boundaries
- This is a SEPARATE computation from the Reports Dashboard. It uses `transactions` directly because it needs product-level breakdown.
- The `monthlyRevenue` here may differ from `getMonthlySalesReport().total` because this one reads from `transactions` (with a 1000 limit) while the other reads from `daily_sales` (no limit). For authoritative monthly totals, always use `daily_sales`.

## 2. Quota & Progress

### 2.1 Monthly Quota

- Source of truth: `settings/general.monthlyQuota` (single Firestore document)
- Read via `SettingsService.getSettings()` (real-time listener with `shareReplay(1)`)
- This value is set by ADMIN in the Settings page via `SettingsService.saveSettings()`

### 2.2 Quota Progress Percentage

- Formula: `Math.min((monthlySalesTotal / monthlyQuota) * 100, 100)`
- `monthlySalesTotal` MUST come from `ReportStateService.getMonthlyReport(year, month).total` (which reads from `daily_sales`)
- `monthlyQuota` MUST come from `SettingsService.getSettings().monthlyQuota`
- Capped at 100% via `Math.min(..., 100)`
- Used in: `QuotaStatusWidget`, `MonthlySalesReport`, `SalesAnalytics`
- All three MUST use the same two data sources. If any component computes quota progress differently, it is a bug.

### 2.3 Daily Target

- Formula: `remainingQuota / remainingDays`
- `remainingQuota = Math.max(monthlyQuota - monthlySalesTotal, 0)`
- `remainingDays = lastDayOfMonth - today + 1` (include today)
- `lastDayOfMonth = new Date(year, month + 1, 0).getDate()`
- If `monthlyQuota === 0`, daily target is `0`
- If `remainingDays <= 0`, daily target is `0`

### 2.4 Quota Status Colors

- `green`: percentage >= 100%
- `yellow`: percentage >= 75%
- `orange`: percentage >= 50%
- `red`: percentage < 50%
- `neutral`: quota is 0 (not configured)

## 3. Shift & Cash Register

### 3.1 Shift Totals

- All shift totals are maintained atomically on the `shifts/{id}` document using Firestore `increment()`:
  - `totalSales`: incremented by sale amount (legacy field, equals totalRevenue)
  - `totalRevenue`: incremented by sale amount
  - `totalCashSales`: incremented by sale amount when `paymentMethod === 'CASH'`
  - `totalGcashSales`: incremented by sale amount when `paymentMethod === 'GCASH'`
  - `totalExpenses`: incremented by expense amount
  - `totalFloatIn`: incremented by float-in amount
  - `totalFloatOut`: incremented by float-out amount
- These are NEVER computed client-side by summing the embedded `transactions[]` array (except during `recalculateShiftTotals()` which is a repair operation).

### 3.2 Expected Closing Balance

- Formula: `openingBalance + totalCashSales + totalFloatIn - totalExpenses - totalFloatOut`
- Maintained atomically via `increment()` on the shift document:
  - CASH sale: `increment(amount)`
  - GCASH sale: no change (GCash doesn't affect physical cash drawer)
  - Float In: `increment(amount)`
  - Expense: `increment(-amount)`
  - Float Out: `increment(-amount)`
- NEVER recompute this client-side except in `recalculateShiftTotals()`

### 3.3 Shift Variance (Discrepancy)

- Formula: `actualClosingBalance - expectedClosingBalance`
- Computed ONCE when closing the shift in `CashRegisterService.closeShift()`
- Stored in `shifts/{id}.discrepancy`
- Display classification:
  - `variance === 0` → "Balanced"
  - `variance < 0` → "Shortage" (money missing)
  - `variance > 0` → "Overage" (extra money)
- Utility functions in `cash-register.utils.ts`: `calculateVariance()`, `getVarianceType()`

### 3.4 Net Cash Flow

- Formula: `(totalSales + totalFloatIn) - (totalExpenses + totalFloatOut)`
- Computed in `cash-register.utils.ts`: `calculateNetCashFlow(shift)`
- Display only — not stored in Firestore

### 3.5 Void Impact on Shift

- When a transaction is voided, the corresponding shift totals are decremented atomically:
  - Sale void: decrement `totalRevenue`, `totalSales`, and either `totalCashSales` or `totalGcashSales`
  - CASH sale void: also decrement `expectedClosingBalance`
  - GCASH sale void: `expectedClosingBalance` unchanged
- The embedded `CashTransaction` in the shift's `transactions[]` array is marked `voided: true`
- Handled in `CashRegisterService.getVoidTransactionShiftUpdates()` (pre-calculates) and applied atomically in `TransactionService.voidTransaction()` batch

## 4. Membership Renewal

### 4.1 Renewal Cycle

- Duration: 30 days from base date
- Base date logic:
  - If current expiration exists AND is in the future → base = current expiration (stacking)
  - Otherwise → base = now
- New expiration: `baseDate + 30 days` via `setDate(getDate() + 30)`
- Applied in `MemberService.renewMembership()` and `MemberService.renewTraining()`

### 4.2 Auto-Renewal on Purchase

- Triggered in `CheckoutService.checkout()` AFTER the batch commit (non-blocking)
- Membership renewal: if any purchased product has `category === 'Training'` AND name includes `'rental'`
- Training renewal: if any purchased product has `category === 'Training'` AND name includes `'personal'` or `'session'`
- Product matching is case-insensitive (`toLowerCase().includes()`)
- If renewal fails, the error is logged but the transaction is NOT rolled back (already committed)

### 4.3 Membership Status

- `Active`: member is registered (default for new members)
- `Inactive`: manually set by staff
- `Pending`: intermediate state
- `membershipExpiration`: only set when a monthly subscription is purchased. `null` means no subscription (walk-in member).
- A member with `status: 'Active'` and `membershipExpiration: null` is a valid walk-in member — NOT a bug.

## 5. Attendance

### 5.1 Volume Analytics

- "Daily volume" = unique member visits per day (deduplicated by `date + memberId`)
- "Hourly traffic" = total check-ins per hour (NOT deduplicated)
- Computed in `ReportsService.getVolumeAnalytics()` from `attendance` collection
- Peak hours = top 5 hours by total check-in count

### 5.2 Top Attendees

- Counted by unique visit DAYS per member (not total check-ins)
- A member checking in twice on the same day counts as 1 visit
- Computed in `ReportsService.getTopAttendees()`, returns top 10

## 6. Date & Timezone Rules

### 6.1 Local Date String

- All date keys (daily_sales doc IDs, attendance `date` field) use LOCAL timezone
- Generated by `toLocalDateStr(date)` or `getLocalDateString(date)` from `date.utils.ts`
- Format: `YYYY-MM-DD`
- NEVER use `toISOString().split('T')[0]` for date keys — that produces UTC dates which shift at midnight in non-UTC timezones

### 6.2 Firestore Timestamps

- Store as Firestore `Timestamp` in the database
- Transform to `Date` only in the view layer (templates, display logic)
- Safe conversion pattern: `value.toDate ? value.toDate() : new Date(value)`

## 7. Void Transaction Rules

### 7.1 What Gets Reversed

- Product stock: incremented back (`increment(item.quantity)`)
- Transaction status: set to `'VOID'`
- Daily sales: decremented (`increment(-totalAmount)`)
- Shift totals: decremented atomically (see 3.5)
- Inventory log: new `AUDIT_ADJUSTMENT` entry created for audit trail

### 7.2 What Does NOT Get Reversed

- Membership renewal triggered by the original sale (if any)
- The original inventory log entries (SALE type) — they remain for audit trail
- The transaction document itself — it's marked VOID, not deleted

### 7.3 Atomicity

- ALL void operations (stock revert, transaction status, daily_sales, shift totals) MUST be in a single `writeBatch`
- Computed in `TransactionService.voidTransaction()` with pre-fetched shift updates from `CashRegisterService.getVoidTransactionShiftUpdates()`
